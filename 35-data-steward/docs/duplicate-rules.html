How the duplicate finder decides two records are the same

A business system can end up with the same customer, supplier or product entered twice. This tool reads every record, looks for pairs that seem to be the same, and suggests merges. It never merges anything itself. A person reads each suggestion and decides.

Fixed rules, no guessingThe same records always give the same answer, so anyone can check it.
Clues add up to a scoreEach matching detail adds points, from 0 up to 1.
A person has the last wordThe tool only suggests. Nothing on the system changes.
1

Tidy each record before comparing

People type the same thing in different ways. Before comparing, the tool rewrites each detail in one standard form, so small typing differences don't hide a match.

Record AShree Ganesh Traders Pvt. Ltd.
Record BGanesh Shree Traders
Different as typed.
+91 98200 12345→9820012345 Phone numbers: only the last ten digits count, so country codes and spaces don't matter.
Elbow 25mm→same as “Elbow 25 mm” Products: a number stuck to its unit counts the same as one with a space.
N/A, Unknown, TBD, phone 0000000000→(treated as empty) Filler values are not evidence. Two records that both say “N/A” are not a match.

Records left out completely: customers and suppliers whose privacy setting is anything other than normal, or missing. They are counted, never compared.

2

Pick which pairs are worth a look

Comparing every record with every other would take far too long. So the tool only compares two records when they already share something: the same email, phone, customer code, website or product code, the same full name, or at least one word of the name (three letters or longer).

  • Shared inboxes don't count. If more than 5 records share one email, phone or code, it is probably an office switchboard or a dummy value, so it is not used to pair records or as evidence.
  • Very common words are skipped. If more than 50 records share one name word, such as “supply”, that word is too common to pair on. The report says how many were skipped.

What “similar name” means: after tidying, the two names are at least 90% alike, about one or two letters apart (“Meera Iyer” and “Meera Iyre”). For products, it also counts when one name is the other with extra words added, like a brand in front (“Arlo Door Closer Heavy” and “Door Closer Heavy”). The shorter name needs at least three words, and no added word may contain a number, because a number is usually a size or a model.

4

Hold back pairs with a warning sign

Some pairs have a reason for doubt. If such a pair scores 0.60 or more, it is never proposed as a merge, even at 0.90 or above. It goes to a person for review, and the report says why. Below 0.60 it stays unlisted either way.

  • A key detail disagrees. Both records have a customer code, email or phone (for products: a code or SKU), and the values are different.
  • Names are only similar and there is no matching customer code (customers and suppliers only). Two people a letter apart can share a family email or phone.
  • Different roles (customers and suppliers only). For example, one record is a customer and the other a supplier.

For products, a code stored in the other record's SKU field is not a disagreement, as long as their other codes don't conflict.

6

Rule out pairs that must not be merged

Some pairs score 0.60 or more, but a rule says they must not be merged. These are listed as “ruled out”, with the reason, and never suggested as a merge.

Customers and suppliers

  • Someone already marked one of them as an allowed duplicate
  • They belong to different companies in the system
  • Different party types, such as a person and an organisation

Products

  • They belong to different companies
  • Different item types
  • Different units, such as boxes and pieces
  • One is a variant of the other (its code is listed among the other's variants)
7

Suggest which record to keep

For each pair, the tool suggests which record should stay if the merge is approved. It goes down this list and stops at the first step that tells the two apart:

  1. More linked records. The one with more orders, payments, deals and other records pointing at it. A merge would have to move each link, so keeping the busier one moves fewer. Counted for proposed merges only.
  2. Created earlier. The older record.
  3. More fields filled in. The more complete record.
  4. First ID in text order. A plain tie-breaker, so the answer is always the same.

If a step can't be checked, for example because a creation date is missing, it is skipped and the report says so. The report also lists each field where the two records differ. Hidden fields, and private ones like tax IDs or bank details, are never shown.

Then a person decides

The tool writes a report and stops. It does not merge, edit or delete anything. A person reads each pair, marks it accepted or rejected, and makes any change through the business system with the usual approval.

The rules described here are rules version 3, frozen so that the held-back accuracy check stays valid. Examples and names on this page are invented; no real customer or product data is shown.
